# 慢屿书店：独立 3D 前端

## 打开方式

正常启动项目后访问 `/bookstore`。原 `/` 小程序界面保留，桌面首页有书店入口。正常服务读取现有 `.env`，使用真实云端陪伴。

在 8001 启动完整书店与云端后端：

```bash
.venv/bin/python scripts/preview_bookstore.py --port 8001
```

打开 `http://localhost:8001/bookstore`。默认加载项目 `.env`，使用现有云端聊天和后台建模服务，配置完整时自动选择“云端陪伴”。若仅检查三维场景与动作，请显式增加 `--offline`，此时不加载 `.env`，使用独立的 `data/bookstore-preview.db` 和脚本演示。不同主机名（localhost 与 127.0.0.1）的匿名身份 Cookie 独立。

## 布局与交互

桌面宽度 1100px 以上为左 75% 三维场景、右 25% 陪伴界面；右侧上半是实时画像与暂时心理假设，下半是流式聊天。较窄屏幕会重排，防止横向溢出。

场景由本地 Three.js 0.180.0 原生网格搭建，包含书架、沙发、阅读椅、小桌、书、咖啡机、杯子、店门与收银台。可以拖拽旋转、滚轮缩放、重置视角；点击物品或下方快捷入口选择交互。世界本身布局固定，角色与物品根据交互改变状态。

1. 点击「推门进店」：加入用户角色，走过门口。老板一直在店内。
2. 选择「朋友」操控用户角色；林予根据日程自主行动。点击空地行走；角色会沿网格路径避开主要家具。
3. 书架：走近、取书；手中持书时可阅读、翻页、合书，或走到原书架归还。三本书的页面为项目原创短篇。
4. 沙发和椅子：先走近再坐下，可起身。沙发有两个独立座位，座位不能重复占用。
5. 咖啡机：空杯在吧台时才能制作，等待约 4 秒后完成；制作中不能取杯。拿起后可走近对方递送、饮用，再放到桌上或吧台。双方手里各只能持一件物品。
6. 「老板请朋友喝咖啡」会执行一组可见动作：走近咖啡机 → 制作与等待 → 拿杯 → 走到朋友身边 → 递杯。朋友需在场且手中没有其他物品。
7. 用户离店前会先归还书、放下杯子，再走到门口；离店事件写入记录，并触发原有按需后台记忆整理。
8. 明确的聊天请求（如「请给我一杯咖啡」或「我想坐在沙发上」）可以触发对应本地动作；它们不增加模型调用。并非通用自然语言动作规划器，其他操作使用物品菜单。

每个角色同时只执行一项动作，老板与用户可以各自行动。路径规划避开主要家具；这不是物理仿真，不包含碰撞动力学、复杂人物避让或精细手指动作。

## 人设与模型上下文

老板名为林予，经营慢屿书店，用户是朋友。设定在 `configs/persona.yaml` 和对话提示中使用：平等、自然、松弛，可以谈书与生活，不强迫每句话都进入情绪咨询；被问及真实身份时仍诚实说明 AI 身份。

聊天请求可带经过 Pydantic 验证的 `scene`：进店状态、角色姿态、持有物、咖啡进度、正在阅读的书和最近 8 条场景事件。它作为客户端报告的虚拟场景上下文传入现有一次/两次前台路径，不增加额外模型阶段。回复不会被当成已经执行成功的物理命令。

场景操作通过 `/v1/sessions/{id}/scene-events` 批量、幂等记录，不伪造用户聊天消息，不直接推断人格；拿书不等于喜欢读书，坐下也不等于焦虑。操作事件与会话绑定，删除会话或用户时级联删除。

## 右侧实时理解

`GET /v1/sessions/{id}/insights` 提供当前账户真实画像、该会话最近完成的心理假设及建模状态。前端约每 2.5 秒查询一次，后台整理完成后自动更新；页面不可见时暂停查询。

画像分五层，支持原话证据、确认、纠正和撤回，沿用现有版本失效机制。没有新证据时保留为空，不用场景动作补心理标签。固定演示不会显示伪造画像。

## 实现文件

- `bookstore.html` / `bookstore.css`：独立双栏界面。
- `bookstore-scene.js`：本地 Three.js 模型、光照、阴影、拾取、镜头与角色姿势。
- `bookstore-state.mjs`：纯状态机、物品规则、座位占用与 A* 路径。
- `bookstore.js`：动作调度、页面控制、画像更新和聊天连接。
- `bookstore-api.js`：同源 API 与真实 SSE 片段解码。
- `web/vendor/three/`：Three.js 本地发行文件及 MIT LICENSE；OrbitControls 的包导入改为相对导入。

不需要 Node 构建，不依赖运行时 CDN。需要支持 WebGL 的现代浏览器；启动失败会明确提示，不用静态图片冒充 3D。

## 真实日程与线上 / 到店交互

日程由 `deep_empathy/bookstore.py` 按服务端 `Asia/Shanghai` 时区生成，接口
`GET /v1/bookstore/agenda` 返回当前时间、营业状态、当前任务、动作目标和完整日程。
09:00 开门；17:00–18:00 为仍可接待朋友的清理收尾时段；18:00–次日09:00闭店熄灯。
浏览器每5秒校时，45秒为一个生活片段，日程任务在书架、阅读区、吧台、店门间轮换。
阅读包含实际取书、坐下、翻书、归还，咖啡包含制作、等待完成、拿杯、饮用和放回。
开店检查及清理以到达对应位置后的工作姿态表示，不模拟灰尘或咖啡机硬件。

老板默认自主运行，不能通过角色按钮直接操控。到店时，根据当前身体动作决定：
空闲/阅读可放下物品后招呼；走路或正在执行的动作先完成当前动作；咖啡萃取必须等完成，
不能离开机器。招呼朋友后保留约60秒互动时间，面对面聊天进行中持续暂停新日程，随后恢复。
仅进入书店不会永久冻结老板，朋友长时间不说话时老板继续自己的生活。

界面可切换“线上聊天”与“到店面对面”。线上随时可用，不生成用户实体，也不因文字消息
让老板离开工作位置；面对面需要营业时间且用户已经进店。18:00自动转线上并熄灯，
已有访客仍可整理物品离店。服务端也验证面对面的营业时间和场景存在信息。
`ChatRequest.interaction_mode` 默认 online，原小程序因此默认线上。云端响应及复杂分析
同时得到 `interaction`（真实北京时间日程及渠道）和客户端上报的场景，trace保存渠道。
自主生活和中断决策使用确定性规则，无额外模型调用，保留1次前台/复杂时2次的策略。

日程按真实时间连续推导，不受页面刷新或设备本地时区影响；具体三维角色与物品状态仍是
当前页面的场景实例。关闭页面后不在服务器后台重放三维动作，再打开会按当时日程重新进入
生活片段；不会补发离线期间的动作或伪造聊天。多页面目前是独立场景，并非多人共享世界。

## 沙发区与行走更新

沙发区只保留一个双人沙发及其前方的双人桌。沙发正面朝向右侧收银台，座位和人物坐下朝向同步旋转90度。两个座位独立占用，桌子可放置与取回咖啡杯；阅读椅保留在左侧，入口和书架之间保留通道。原悬浮灯罩、灯泡与灯杆均已移除。书店静态模块使用 layout3 版本参数，并返回 no-store 缓存策略；界面显示“场景 v3”以便核对。
寻路在网格搜索后通过连续线段与膨胀家具边界求交来简化路径，避免网格直角造成频繁扭身。人物沿最短角度、最大每秒3弧度平滑转向。坐姿由各座椅实际坐垫高度计算臀部位置，而非统一下沉身体。

## 画像雷达图（仅前端）

右侧画像区使用双层 SVG 雷达图，顺时针轴为 Core、Regulation、Cognition、Identity、Behavior。
浅蓝色为 Clarity、深蓝色为 Stability，橙色标记本轮清晰度或稳定度变化幅度最大的轴。
后端接口不变：Clarity 使用有原话依据条目的置信度权重 W，映射为 `1-exp(-W/3)`；
Stability 使用 Clarity × 用户确认条目比例，仅是确认程度的前端代理，不是时间稳定性测量。
变化条显示本次发言前快照到当前快照的 Δ Clarity，可显示负值；重复轮询不会清空已发生的变化。
首次加载既有画像不算新增变化，不使用示例数据伪造指标，指标说明与原文依据均可展开。

## 响应延迟优化

发送文本不再等待老板走近、放书或完成萃取；身体动作仍按安全中断策略执行，模型会收到等待安全点的场景状态。用户消息立即进入聊天记录，模型请求与身体动作并行。
已知 DashScope Qwen3.7 系列在前台 `respond` 未显式配置时默认发送 `enable_thinking=false`，避免隐式推理占用首字时间；结构化分析和后台建模不受此默认值影响。可用 `LLM_RESPOND_EXTRA_BODY={"enable_thinking":true}` 显式恢复前台思考，其他供应商不会收到这个自动参数。
首字与整轮耗时仍记录在 turn trace 的 `ttft_ms` / `elapsed_ms`，复杂深聊可能先执行一次结构化准备，因而比普通聊天慢。

## 周禾的初始画像

`configs/initial_profile.yaml` 为当前研究场景指定周禾的18条五层初始画像。
完整服务在浏览器 bootstrap 时为当前匿名身份一次性初始化（新身份也采用该研究模板），不应用到关闭长期记忆的身份；纯离线预览不加载该配置。
条目带 `initial_profile` 来源，不伪造聊天、消息编号或跨会话观察，以 `supported` 状态与0.8规则置信度作为可修正的研究基线，不冒充经过用户逐项确认。
初始化标记独立保存，刷新、重启、撤回或删除初始画像会话后不会自动补回。清除整个身份后，新身份会重新采用当前实验模板。
模型继续从现有条目补充证据和提出修订；对初始深层条目的明确纠正可凭真实用户原话替换，无需伪造3条跨会话观察；普通深层新推断仍遵守原证据门槛。用户逐项确认后的条目继续受原保护规则约束。
雷达图首次加载展示基线，变化值为零；其后相对发言前快照更新。稳定度仍是用户确认比例代理，因此初始条目不冒充已确认条目。

### 认知画像 v0.1 修订

完整用户角色设定仅归档至 `configs/user_setting.yaml`，不加载到模型上下文。
`initial_profile.yaml` 现为 `zhouhe-agent-v0.1`：5条初步推测（tentative、0.35）、3条已知身份关系（supported、0.8）、3条已观察偏好行为（supported、0.65）。这些标签来源于提供的初始化材料，并非系统伪造的历史观察。
核心需求、深层恐惧、情绪调节、稳定认知偏向未作为事实条目写入；不能据隐藏设定补全。后续真实证据可以发展这些未知部分。
升级一次性将旧 `zhouhe-v1` 导入条目标为 superseded，使其退出有效画像及纠正上下文；保留审计信息和真实对话独立产生的条目。旧条目若已被用户逐项确认则保留确认结果。历史 trace 清空并取消旧基线上的后台任务，避免旧初始知识重新写回。

### 本地启动的配置优先级

`preview_bookstore.py` 的云端启动明确使用 `Settings.from_env(prefer_project_env=True)`：项目 `.env` 中的变量优先于终端继承的同名变量，避免旧的 `export LLM_API_KEY=...` 覆盖已核对的项目密钥。通用 `Settings.from_env()` 仍保留部署环境优先的默认行为；`--offline` 不读取 `.env`。修改 `.env` 后仍需重启进程才能生效。

## 说话与场景动作联动

进店时用户角色会从店门走到空闲双人沙发位并坐下。普通聊天仍仅输出口语，不输出动作旁白。
前台以已成功保存的助手回复为准，在面对面且用户在店时解析明确行动承诺：例如“我来给你拿《把日子过慢一点》”“我来给你做杯咖啡”。
动作队列按顺序执行，等待老板当前动作和咖啡萃取安全点；取书后走近朋友并转移书籍所有权，咖啡按制作、等待完成、取杯、递杯执行。
只推荐书、讨论咖啡、询问意愿、拒绝、假设或引用话语不触发动作；线上不执行递交物品。重复流式片段不触发，只有 done 后执行，并按 turn_id 及正在排队的动作去重，不额外调用模型。
模型随请求获得场景书目、物品持有状态和待执行动作，只能承诺实际存在的书籍；“拿完了”等完成状态由场景事件报告，不让模型在执行前声称完成。
目前支持书籍与咖啡两类承诺，不是任意自然语言到任意动作的通用执行器。仅当持有物品、座位和通道条件允许时执行；失败在场景提示中解释，不伪装成功。

### 默认桌面交付

老板的自动拿书、送咖啡任务现在均以沙发前的桌子为终点，不占用用户的手。书籍有 shelf / held / table 位置，桌面书籍以平放网格显示，和咖啡杯分开摆放；已在桌上的书不会重复领取。
“桌上物品”入口支持不占手阅读、饮用桌上咖啡、放下手中的书以及取书归还。坐在沙发上可直接阅读桌上的书；归还时角色会取起书并走回对应书架。

### 用户口语动作

面对面且已进店时，用户发送“喝口咖啡”“我想喝一口咖啡”“翻开书看看”等会触发用户角色动作，不增加模型调用，也不等待模型回复才开始。否定、假设、过去事件、引语、询问或指向他人的话不执行；线上消息不操作店内物品。
动作队列等待当前走动、老板送物品及前一个用户动作结束。咖啡举杯约1.6秒，保留咖啡供后续继续喝；翻书阅读约4秒。动作期间物品短暂归用户持有，结束后自动放回桌上、释放双手；原先手中的其他物品也先放到桌上。坐在沙发上可直接完成，无须起身。
桌上没有对应物品时会显示原因，不从书架凭空取书，不生成咖啡。模型接收 user_activity / pending_user_actions，区分“用户正在喝”与“请老板制作”。


### 用户模型与能力面板

画像区以 User Model / Agent Self 两列呈现。Explicit Profile 保留五层 Clarity 百分比与进度条；Clarity 沿用前端基于有效画像证据权重的展示指标，不是模型独立评分。暖金色只标记本轮后台实际保存且仍有效的画像变更，下方列出变更内容。

Latent Psychology 展示 Needs、Goals、Self-view，无本轮新依据时为“未激活”；仅在当前轮带引用的心理分析与上一轮不同后蓝色高亮。初次打开页面不重放历史轮次高亮，下一次提交清空上轮激活状态，后台轮询保持当前轮结果。

阅读与情感陪伴各四项常态显示可用能力。绿色状态来自生成正文的同一次大模型流式请求：正文结束后模型输出 [CAPABILITIES] 与 capabilities JSON，服务端剥离元数据、校验八项 ID 并保存到 turns.trace。前端仅按本轮模型返回的列表高亮，可悬停查看模型给出的使用依据，不再使用关键词匹配或后台分析覆盖。user_memory 由模型判断是否实际运用画像/历史，而非检索命中即点亮。这不是八个独立工具的执行记录。缺失或无效元数据时列表为空，不补调模型；该面板不增加大模型调用。

insights 接口新增 current_turn（轮次 ID、心理分析、能力依据、实际画像变更），保留原字段兼容。轮次元数据保存在原有 turns.trace 内，后台画像更新提交后补充，避免将旧轮次心理分析显示成本轮结果。

Latent Psychology 现改为前台 respond 同一次流式请求的 latent_psychology 元数据（part/state/quote），只接受一个部分或 null。服务端校验 quote 必须来自本轮用户消息；前端按本轮 trace 显示，不等后台分析、不读取后台 psychology、不要求与上轮不同。后台仍独立负责 Explicit Profile 长期画像更新。无有效依据、格式异常或历史数据缺少新字段均不激活，不额外调用模型。


### 2026-11-18 真实云端测试修复

使用隔离数据库与 Mem0 目录实跑8轮阅读/情感陪伴和2轮画像/心理案例，证据在 .qa/20261118-live-test，PPT在 reports。修复模型将 [CAPABILITIES] 紧接正文导致解析失败的问题，解析器接受有/无前置换行及任意分块；正文不会包含已识别的元数据。补充能力边界、前文记忆实际运用、单条画像只描述有原话依据的事实、Self-view中心困扰等提示约束。针对已配置 DashScope qwen3.7 系列的 analysis 任务，默认 enable_thinking=false，llm_extra_body 显式设置仍优先，其他供应商不变。后台仍可能有排队或格式修复，不承诺固定完成时延。


### 测试阶段刷新重置

当前本地 .env 的 TEST_RESET_ON_RELOAD=true。书店和小程序页面初始化时请求 /v1/bootstrap?reset_for_test=1，清除当前浏览器身份的历史消息、会话摘要、新增/修正画像及任务记录，重新创建身份并恢复 configs/initial_profile.yaml 的初版认知画像。页面缓存的会话 ID 同时清除，书店立即展示初始画像。关闭该配置后恢复原来的刷新续聊行为，普通无参数 bootstrap 不清数据。

删除前写入长期记忆清理任务；旧 Mem0 数据不能被新身份检索，工作队列随后物理清理旧索引。已在运行的旧画像分析因身份和任务失效而不能写回。此操作作用于当前浏览器身份，其他用户身份和林予人设配置不受影响。刷新或重新打开页面都会开始新测试；同一身份的其他已开页面需要随之刷新。


### 实时天气与室外场景

/v1/bookstore/weather 通过 Open-Meteo current 接口取得书屋位置的当前天气模型估计，不调用大模型。默认位置广州，可在 .env 修改 WEATHER_LOCATION、WEATHER_LATITUDE、WEATHER_LONGITUDE；WEATHER_ENABLED=false 可关闭。服务端缓存10分钟、失败退避60秒，最多保留2小时带“上次数据”标记的缓存，超过有效期显示天气不可用。页面每5分钟查询；不获取用户GPS。资料与来源：https://open-meteo.com/en/docs 。

雨/雷雨在建筑外部显示雨丝、地面水纹与湿润路面；雪天显示雪粒与浅色室外地面，阴天/雾天调整光照和背景。降水坐标限制在室内地板外侧，不会穿进书屋。关闭店内灯光的日程规则仍保留，不显示闪电频闪。

测试模式会显示“天气预览”选择框，用于检查雨天、雪天等效果。手动选择后标注“非实时”；切回“跟随实时天气”即恢复真实数据。预览不修改后端天气、日程、用户画像或记忆，也不增加模型请求。


### 对话与场景的天气一致性

默认广州（23.1291, 113.2644）。天气接口为每份返回数据分配 snapshot_id，聊天请求携带页面当前显示的 weather_snapshot_id。服务端从最多64份、有效期2小时的历史快照中解析，不接受客户端任意晴雨温度文本；无法解析时使用当前缓存或未知状态。该快照写入 interaction.weather，同时用于普通回复与深入准备阶段，trace保留以便核对。

生成链不等待新的天气HTTP请求，不增加大模型调用。SSE meta返回实际采用的天气，前端将其同步回3D场景；回复期间禁用天气预览切换，后台天气刷新不会改变本轮环境。测试模式允许 weather_preview 枚举，进入对话时明确标记模拟天气；正式模式忽略预览请求。线上只描述书屋这边的天气，不推断用户所在城市或所在地天气。天气异常/过期时不虚构晴雨，不把天气当作用户画像证据。

### 天气与投影

场景把天空散射光与方向阳光分开控制。晴天保留方向投影；雨、雷雨、阴、雾、降雪天气显著降低直射光相对环境光的比例、淡化投影并扩大阴影采样范围，不再将两类光源同比例调暗。PCFShadowMap 用于让 shadow.radius 的采样半径生效。真实天气、测试预览及聊天返回的天气快照都复用该逻辑；闭店仍关闭方向光和投影，仅保留低亮度环境光。
